# Übung M06: OpenAPI `securitySchemes` & kombinierte Sicherheitsanforderungen

## 1. Szenario und Zielzustand

Du prüfst die neue OpenAPI-3.1-Spezifikation eines Partnerportals und vergleichst die Darstellung im **Interaktiven Lernstudio**, in **Swagger Web UI** (`https://petstore3.swagger.io/`) und in **Bruno Desktop**.

## 2. Aufgabenpakete

### Aufgabe A: Vier Sicherheitsregeln im Lernstudio & in OpenAPI 3.1 modellieren
1. Teste zuerst alle vier Sicherheitsmodi im [Interaktiven Lernstudio → 2. OpenAPI Security Tester](https://chatelao.github.io/api-schulung/#labs:openapi).
2. Erstelle eine Kopie von [openapi-security-demo.yaml](https://github.com/chatelao/api-schulung/blob/main/01-module/M06-openapi-security-schemes/openapi-security-demo.yaml) unter dem Namen `partner-openapi.yaml` und ergänze einen fünften Pfad `/anything/oidc-profile`, der:
   - Das globale `bearerAuth` **nicht** verwendet, sondern `oidcAuth` mit Scope `openid` fordert.
   - Für eine `PUT`-Operation auf `/anything/admin` zusätzlich `apiKeyAuth` **UND** `mtlsAuth` verlangt.

### Aufgabe B: Typische Schema-Fehler finden und beheben
Analysiere das folgende fehlerhafte Snippet und korrigiere alle drei Fehler:
```yaml
openapi: 3.0.3
components:
  securitySchemes:
    mtls:
      type: mutualTLS
    key:
      type: apiKey
      in: header
      name: X-Key
paths:
  /public:
    get:
      responses: { "200": { description: "OK" } }
  /either:
    get:
      security:
        - key: []
          bearer: []
      responses: { "200": { description: "OK" } }
```

### Aufgabe C: GUI-Import in Bruno Desktop & Swagger-UI-Vergleich
1. Importiere deine `partner-openapi.yaml` in **Bruno Desktop** (*`+` → Import Collection → OpenAPI V3 Specification*) und prüfe im Auth-Tab der erzeugten Requests, welche Authentifizierungsarten Bruno übernommen hat.
2. Öffne **`https://petstore3.swagger.io/`** und klicke auf **Authorize**, um dieselben `securitySchemes` in einer echten Swagger Web UI zu betrachten.

### Bonus-Challenge D: OpenAPI 3.2 Device-Flow-Ausblick
Recherchiere bzw. skizziere das Schema für `oauth2MetadataUrl` und `flows.deviceAuthorization` in OpenAPI 3.2 (inkl. `deviceAuthorizationUrl`, `tokenUrl` und `scopes`).

## 3. Gestufte Hilfestellungen

<details>
<summary>Tipp 1 (Konzeptionell): Worauf muss man bei ODER vs. UND achten?</summary>

Ein Bindestrich `-` in YAML startet ein neues Listenelement im `security`-Array. Zwei Schemas unter demselben Bindestrich bedeuten **UND**; zwei separate Bindestriche bedeuten **ODER**.

</details>

<details>
<summary>Tipp 2 (Konkret): Korrektur des fehlerhaften Snippets in Aufgabe B</summary>

1. `openapi: 3.1.0` statt `3.0.3` (sonst ist `type: mutualTLS` ungültig).
2. `/public` braucht `security: []`, falls globales `security` aktiv ist (und `bearer` muss unter `securitySchemes` deklariert sein).
3. `/either` braucht zwei separate Array-Einträge (`- key: []` und `- bearer: []`) für **ODER**.

</details>

## 4. Selbstkontrolle (Definition of Done)

- [ ] Die vier Sicherheitsfälle (`security: []`, `A ODER B`, `{} ODER A`, `A UND B`) sind syntaktisch korrekt modelliert.
- [ ] Alle drei Fehler aus Aufgabe B wurden identifiziert und behoben.
- [ ] `bru import openapi` erzeugt eine sortenreine OpenCollection-YAML-Struktur ohne Fehler.
