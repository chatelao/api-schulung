# Übung M06: OpenAPI `securitySchemes` & kombinierte Sicherheitsanforderungen

## 1. Szenario und Zielzustand

Du prüfst die neue OpenAPI-3.1-Spezifikation eines Partnerportals. Der Vertrag muss vier unterschiedliche Zugriffsregeln eindeutig abbilden und nach einem `bru import openapi` sauber in Bruno nachvollziehbar sein.

## 2. Aufgabenpakete

### Aufgabe A: Vier Sicherheitsregeln in OpenAPI 3.1 modellieren
Erstelle eine Kopie von [openapi-security-demo.yaml](https://github.com/chatelao/api-schulung/blob/main/01-module/M06-openapi-security-schemes/openapi-security-demo.yaml) unter `/tmp/partner-openapi.yaml` und ergänze einen fünften Pfad `/anything/oidc-profile`, der:
1. Das globale `bearerAuth` **nicht** verwendet, sondern `oidcAuth` mit Scope `openid` fordert.
2. Für eine `PUT`-Operation auf `/anything/admin` zusätzlich `apiKeyAuth` **UND** `mtlsAuth` verlangt.

### Aufgabe B: Typische Schema-Fehler finden und beheben
Analysiere das folgende fehlerhafte Snippet und korrigiere alle drei Fehler:
```yaml
openapi: 3.0.3
components:
  securitySchemes:
    mtls:
      type: mutualTLS
    key:
      type: apiKey
      in: header
      name: X-Key
paths:
  /public:
    get:
      responses: { "200": { description: "OK" } }
  /either:
    get:
      security:
        - key: []
          bearer: []
      responses: { "200": { description: "OK" } }
```

### Aufgabe C: Import nach Bruno & Verifikation
Importiere deine OpenAPI-3.1-Datei per `bru import openapi --source /tmp/partner-openapi.yaml --output /tmp/partner-bruno --collection-format=opencollection` und prüfe per YAML-Inspektion, welche Auth-Blöcke Bruno erzeugt hat.

### Bonus-Challenge D: OpenAPI 3.2 Device-Flow-Ausblick
Recherchiere bzw. skizziere das Schema für `oauth2MetadataUrl` und `flows.deviceAuthorization` in OpenAPI 3.2 (inkl. `deviceAuthorizationUrl`, `tokenUrl` und `scopes`).

## 3. Gestufte Hilfestellungen

<details>
<summary>Tipp 1 (Konzeptionell): Worauf muss man bei ODER vs. UND achten?</summary>

Ein Bindestrich `-` in YAML startet ein neues Listenelement im `security`-Array. Zwei Schemas unter demselben Bindestrich bedeuten **UND**; zwei separate Bindestriche bedeuten **ODER**.

</details>

<details>
<summary>Tipp 2 (Konkret): Korrektur des fehlerhaften Snippets in Aufgabe B</summary>

1. `openapi: 3.1.0` statt `3.0.3` (sonst ist `type: mutualTLS` ungültig).
2. `/public` braucht `security: []`, falls globales `security` aktiv ist (und `bearer` muss unter `securitySchemes` deklariert sein).
3. `/either` braucht zwei separate Array-Einträge (`- key: []` und `- bearer: []`) für **ODER**.

</details>

## 4. Selbstkontrolle (Definition of Done)

- [ ] Die vier Sicherheitsfälle (`security: []`, `A ODER B`, `{} ODER A`, `A UND B`) sind syntaktisch korrekt modelliert.
- [ ] Alle drei Fehler aus Aufgabe B wurden identifiziert und behoben.
- [ ] `bru import openapi` erzeugt eine sortenreine OpenCollection-YAML-Struktur ohne Fehler.
