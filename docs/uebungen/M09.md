# Übung M09: OAuth 2.0 vs. RFC 9700 & OAuth 2.1

## 1. Szenario und Zielzustand

Im Rahmen eines Security-Reviews prüfst du den Keycloak-Client `bruno-pkce-client` auf Konformität mit **RFC 9700** und **OAuth 2.1**. Du spielst den **Authorization Code + PKCE**-Flow visuell im Browser-Debugger durch und weist nach, dass unsichere Alt-Verfahren (**Implicit**, fehlendes PKCE, **`plain`**) abgewiesen werden.

## 2. Aufgabenpakete

### Aufgabe A: PKCE-Flow im Browser-Debugger nachvollziehen
1. Öffne `http://localhost:8090/default/debugger` im Browser.
2. Starte einen vollständigen Login-Durchlauf (z. B. Benutzer `alice`) und notiere die drei Stationen: (1) `/authorize` Request, (2) erhaltener Einmal-`code` in der Rücksprung-URL, (3) Tausch gegen `access_token` an `/token`.

### Aufgabe B: Härtungs-Audit gegen Keycloak (`bruno-pkce-client`) in Bruno / Browser
Teste in **Bruno Desktop** (im Tab *Settings → Follow Redirects: OFF*) oder direkt im Browser die folgenden drei unzulässigen Anfragen gegen `http://localhost:8081/realms/api-lab/protocol/openid-connect/auth` und notiere jeweils die Fehlermeldung im `Location`-Header:
1. `response_type=token` (Implicit Grant) → `?client_id=bruno-pkce-client&response_type=token&redirect_uri=http://localhost:8080/callback&scope=openid`
2. Authorization Code **ohne** `code_challenge` → `?client_id=bruno-pkce-client&response_type=code&redirect_uri=http://localhost:8080/callback&scope=openid`
3. PKCE mit Methode **`plain`** → `?client_id=bruno-pkce-client&response_type=code&redirect_uri=http://localhost:8080/callback&scope=openid&code_challenge=TestVerifier123456789012345678901234567890123&code_challenge_method=plain`

### Aufgabe C: Code-Interception-Abwehr erklären
Erkläre in 3 eigenen Sätzen:
1. Warum ein Angreifer, der den `code` abfängt, ohne den `code_verifier` kein Token bekommt.
2. Warum **Implicit Grant** und **ROPC (`grant_type=password`)** in OAuth 2.1 gestrichen wurden.

### Bonus-Challenge D: Legacy-ROPC-Client in Keycloak-Konfiguration finden
Öffne [lab/keycloak/realm-import.json](https://github.com/chatelao/api-schulung/blob/main/lab/keycloak/realm-import.json) in einem Editor und identifiziere, welcher der vier Clients bewusst als `DEPRECATED` für Migrations-Audits markiert ist und an welchem JSON-Feld man erkennt, dass der veraltete Password-Grant erlaubt ist.

> **Hinweis:** Die manuelle PKCE-`S256`-Berechnung per `openssl` & `curl` findest du in [Advanced A05](../advanced/A05.md).

## 3. Gestufte Hilfestellungen

<details>
<summary>Tipp 1 (Konzeptionell): Warum antwortet Keycloak bei fehlerhaften Parametern mit 302 statt 400?</summary>

Wenn die `redirect_uri` gültig ist, schickt der Authorization Server Fehler standardmässig gemäss RFC 6749 §4.1.2.1 als Weiterleitung (`302 Found`) mit `?error=...` zurück an die Client-Callback-URL. Nur bei ungültiger `redirect_uri` bricht er direkt mit `400 Bad Request` ab.

</details>

<details>
<summary>Tipp 2 (Konkret): Gesuchtes Feld in realm-import.json für Bonus D</summary>

Suche in `lab/keycloak/realm-import.json` nach `"directAccessGrantsEnabled": true` — das ist Keycloaks Name für den veralteten Resource Owner Password Credentials (ROPC) Grant.

</details>

## 4. Selbstkontrolle (Definition of Done)

- [ ] Der Ablauf von Authorization Code + PKCE wurde im `mock-oauth2` Browser-Debugger nachvollzogen.
- [ ] `Implicit`, fehlendes PKCE und `plain` werden von `bruno-pkce-client` nachweisbar abgewiesen (`unauthorized_client` / `invalid_request`).
- [ ] Du kannst den Schutzmechanismus von PKCE sowie das Verbot von Implicit/ROPC erklären.
