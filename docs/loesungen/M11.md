## Lösung Aufgabe B: Kontrast ID Token vs. Access Token

1. **Zielgruppe (`aud`):** ID Token enthält `bruno-pkce-client`; Access Token enthält `api-lab-orders` (und `account`).
2. **Typ (`typ`):** ID Token = `"ID"`, Access Token = `"Bearer"`.
3. **Berechtigungen:** Nur das Access Token enthält `scope` und `realm_access.roles` für API-Autorisierung.
4. **Verwendung:** `/userinfo` akzeptiert ausschliesslich das Access Token (`200 OK`). Ein ID Token als Bearer-Token an `/userinfo` oder eine Fach-API zu senden, ist ein Sicherheitsverstoss und wird mit `401` abgewiesen.

## Lösung Aufgabe C: OpenAPI 3.1 `openIdConnect`

```yaml
components:
  securitySchemes:
    labOidc:
      type: openIdConnect
      openIdConnectUrl: http://localhost:8081/realms/api-lab/.well-known/openid-configuration
```

## Lösung Bonus-Challenge D: Signaturprüfung

Beim Ändern eines einzigen Zeichens im Payload (z. B. `"sub"` verändern) bleibt der Base64URL-Teil per `jq` weiterhin lesbar — die kryptografische RSA-SHA256-Prüfung gegen den öffentlichen Schlüssel aus `jwks_uri` schlägt jedoch sofort fehl (`401 Invalid token`).
