# Modul 12: Token-Lebenszyklus, Sicherheits-Audits & CI/CD-Automatisierung

## 1. Lernziele

Nach Abschluss dieses Moduls kannst du:
1. Das **Revocation-Dilemma** lokal geprüfter JWTs (RFC 9068) erklären und aktive Token-Lebenszyklus-Steuerung mittels **Token Introspection (RFC 7662)** und **Token Revocation (RFC 7009)** **umsetzen**.
2. Erweiterte Schutzmechanismen gegen gestohlene Bearer Tokens (**Sender-Constrained Tokens** über **mTLS RFC 8705** und **DPoP RFC 9449**, Audience-Bindung RFC 8707, Refresh Token Rotation) sicher **einordnen**.
3. Eine automatisierte **Security-Audit-Suite (6 Negativtests)** mit `bru run` headless **ausführen**.
4. Komplette API-Test-Suites inkl. mTLS (`--client-cert-config`), Secrets-Schutz (`--reporter-skip-headers`) und JUnit-Reports in **GitHub Actions** **integrieren**.

## 2. Architektur und Kernkonzepte

Reale Angriffe brechen selten die Kryptografie von OAuth 2.1 — stattdessen stehlen Angreifer gültige Bearer Tokens aus Logs, Browser-Speichern oder kompromittierten Clients.

### Das Revocation-Dilemma selbstenthaltener JWTs

Wenn ein Resource Server ein JWT-Access-Token nur lokal über `jwks_uri` prüft, bleibt ein gestohlenes Token bis zu seinem `exp`-Zeitstempel gültig — selbst wenn der Benutzer sich bereits ausgeloggt hat!

**Gegenmassnahmen:**
1. **Kurze Access-Token-Laufzeiten** (z. B. `accessTokenLifespan: 300s` im Lab) + Refresh Token Rotation.
2. **Token Introspection (RFC 7662):** Der Resource Server fragt beim Authorization Server aktiv nach (`active: true` vs. `active: false`).
3. **Token Revocation (RFC 7009):** Client oder Admin widerruft Tokens explizit beim Logout oder Kompromittierungsverdacht.
4. **Sender-Constrained Tokens:** Bindet das Token kryptografisch an einen Client-Schlüssel, sodass ein gestohlenes Token allein nutzlos ist:
   - **OAuth 2.0 Mutual-TLS Client Authentication & Certificate-Bound Access Tokens (RFC 8705)**
   - **Demonstrating Proof-of-Possession — DPoP (RFC 9449)**

### Vergleichstabelle: Bearer Tokens vs. Sender-Constrained Tokens

| Eigenschaft | Standard Bearer Token (RFC 6750) | mTLS-Bound (RFC 8705) | DPoP (RFC 9449) |
| :--- | :--- | :--- | :--- |
| **Schutz bei Token-Diebstahl** | **Keiner** (wer es hat, nutzt es) | Nur mit Client-Private-Key nutzbar (`cnf.x5t#S256`) | Nur mit Client-Proof-JWT nutzbar (`cnf.jkt`) |
| **Typischer Einsatz** | Interne Backends, Standard-SPAs | B2B, Open Banking, hochregulierte M2M-APIs | SPAs / Public Clients ohne mTLS-Infrastruktur |

## 3. Geführter Walkthrough (`curl` & `Bruno CLI`)

### `curl`: Introspection (RFC 7662) → Revocation (RFC 7009) → Re-Check

Führe [scripts/curl/m12-introspect-revoke.sh](https://github.com/chatelao/api-schulung/blob/main/scripts/curl/m12-introspect-revoke.sh) aus. Ablauf:
1. Client-Credentials-Token von Keycloak holen.
2. `POST /realms/api-lab/protocol/openid-connect/token/introspect` → `"active": true`.
3. `POST /realms/api-lab/protocol/openid-connect/revoke` → HTTP `200 OK`.
4. Erneutes `POST .../token/introspect` → `"active": false`!

### `Bruno CLI`: Die 6 automatisierten Security-Audit-Negativtests

Öffne [collections/bruno/security-audit-suite/](https://github.com/chatelao/api-schulung/blob/main/collections/bruno/security-audit-suite/opencollection.yml) und starte sie headless:

```bash
set -a && source lab/.env && set +a
cd collections/bruno/security-audit-suite
bru run -r --env ci \
  --env-var "m2mClientSecret=${KC_M2M_CLIENT_SECRET}" \
  --reporter-junit /tmp/m12-security-audit.xml \
  --reporter-skip-headers Authorization
```

Die 6 geprüften Angriffs-/Fehlervektoren:
1. `01-invalid-redirect-uri.yml`: Unbekannte `redirect_uri` → HTTP `400`.
2. `02-missing-pkce.yml`: Authorization Request ohne `code_challenge` → HTTP `400`.
3. `03-query-string-token-audit.yml`: Token verbotenerweise als `?access_token=...` → `/bearer` lehnt mit `401` ab.
4. `04-expired-or-invalid-token.yml`: Ungültiges/abgelaufenes JWT gegen `/userinfo` → HTTP `401`.
5. `05-revoked-token-introspect.yml`: Widerrufenes Token liefert `active: false` (`401`/`active: false`).
6. `06-tampered-jwt-header.yml`: Manipulierter JWT-Payload bei unveränderter Signatur → HTTP `401`.

### CI/CD in GitHub Actions (`.github/workflows/verify-labs.yml`)

In der Pipeline laufen sämtliche `curl`-Checks und `bru run -r --env ci`-Suites vollautomatisch nach Start des Docker-Labors, inklusive `--reporter-skip-headers Authorization`, damit keine Tokens in CI-Artefakten landen.

## 4. Typische Fallstricke und Troubleshooting

| Fehlerbild | Ursache | Diagnose & Lösung |
| :--- | :--- | :--- |
| Introspection liefert `401 invalid_client` | `/token/introspect` erfordert Client-Authentifizierung des Resource Servers / Clients | `user = "${KC_M2M_CLIENT_ID}:${KC_M2M_CLIENT_SECRET}"` via `-K -` mitsenden |
| Nach `/revoke` akzeptiert eine andere API das JWT noch kurzzeitig | Resource Server prüft nur lokal per JWKS ohne Introspection | Für hochkritische Endpunkte Introspection aktivieren oder Token-TTL stark verkürzen |
| JUnit-Report in CI enthält vertrauliche Bearer-Header | `--reporter-skip-headers` wurde vergessen | Immer `--reporter-skip-headers Authorization X-Api-Key` bzw. `--reporter-skip-all-headers` setzen |

## 5. Spickzettel (Cheat Sheet)

| Standard / Flag | Bedeutung |
| :--- | :--- |
| **RFC 7662** (`/token/introspect`) | Aktive Server-seitige Token-Statusprüfung (`active: true/false`) |
| **RFC 7009** (`/revoke`) | Expliziter Token-Widerruf |
| **RFC 8705** / **RFC 9449** | Sender-Constrained Tokens via mTLS bzw. DPoP |
| `bru run -r --env ci --bail` | Bricht CI-Lauf sofort beim ersten fehlgeschlagenen Test ab |
| `--reporter-skip-headers Authorization` | Verhindert Token-Leaks in CI-Testberichten |
