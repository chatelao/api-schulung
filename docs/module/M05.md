# Modul 5: Klassische Credentials & Secret-Hygiene (Swagger Web UI & Bruno)

## 1. Lernziele

Nach Abschluss dieses Moduls kannst du:
1. Die Funktionsweise und Sicherheitsgrenzen von **HTTP Basic**, **HTTP Digest**, statischen **API-Keys** und **Bearer Tokens** anschaulich **erklären**.
2. Begründen, warum Base64 bei `Authorization: Basic` **keine Verschlüsselung** ist und weshalb Geheimnisse niemals in URL-Adressen (`?api_key=...`) stehen dürfen.
3. Basic Auth und Bearer Auth direkt in der **HTTPBin Swagger Web UI (`https://httpbin.org/`)** ohne lokale Server-Installation testen.
4. Passwörter und API-Keys in **Bruno Desktop** sauber über **Secret-Variablen** (`secret: true`) vor versehentlichem Hochladen nach Git **schützen**.

## 2. Architektur und Kernkonzepte (ohne Netzwerk-Vorwissen)

Viele ältere oder interne Schnittstellen verlangen vor dem Zugriff ein Passwort oder einen festen Schlüssel (*Credential*). Entscheidend ist nicht nur *dass* du dich anmeldest, sondern **wo** diese Daten übertragen und gespeichert werden:

- **Kardinalregel 1 (Base64 ≠ Verschlüsselung):** Bei HTTP Basic wandelt der Client `benutzer:passwort` in Base64-Text um (z. B. `bGFidXNlcjpnZWhlaW0=`). Jeder kann das sofort zurückübersetzen — deshalb ist HTTP Basic nur über verschlüsseltes **HTTPS** (ab Modul 7) sicher!
- **Kardinalregel 2 (Keine Secrets in URLs):** Steht ein Schlüssel in der Adresszeile (`?api_key=12345`), wird er im Browserverlauf, in Proxy-Protokollen und in Server-Logs im Klartext gespeichert. Schlüssel gehören daher in **HTTP-Header** (z. B. `X-Api-Key`).
- **Kardinalregel 3 (Keine Secrets in Git):** Passwörter dürfen niemals fest in `.yml`- oder `.xml`-Dateien stehen, die du mit dem Team über Git teilst.

### Vergleichstabelle: Klassische Authentifizierungsverfahren

| Verfahren | Wo wird es übertragen? | Schutz ohne HTTPS | Einrichtung in Bruno Desktop / Swagger UI |
| :--- | :--- | :--- | :--- |
| **HTTP Basic** | Header `Authorization: Basic ...` | **Keiner** (nur Base64!) | In Swagger UI über **Authorize** oder in Bruno *Auth → Basic Auth* (`secret: true`) |
| **HTTP Digest** | Challenge-Response (`Nonce` + Hash) | Passwort nicht im Klartext | In Bruno *Auth → Digest Auth* |
| **API-Key (Header)** | Eigener Header, z. B. `X-Api-Key` | **Keiner** | Auth-Tab → *API Key* (`Add to: Header`) |
| **Bearer Token** | Header `Authorization: Bearer ...` | **Keiner** (Besitz = Zugriff) | In Swagger UI über **Authorize** oder in Bruno *Auth → Bearer Token* |

## 3. Geführter Walkthrough (`Swagger Web UI` & `Bruno Desktop`)

### Schritt 1: Zero-Install direkt in der HTTPBin Swagger Web UI (`https://httpbin.org/`)

1. Öffne **https://httpbin.org/** im Browser (keine Installation nötig).
2. Klappe unter **Auth** den Punkt **`GET /basic-auth/{user}/{passwd}`** auf → **Try it out**:
   - Gib `user = labuser` und `passwd = demo-secret` ein → **Execute** → dein Browser fragt nach Benutzername/Passwort (oder sende über Bruno).
3. Klappe **`GET /bearer`** auf → klicke im Formular oder oben bei **Authorize** auf `Bearer`, gib einen Test-Token-String ein und sende → HTTPBin antwortet mit `"authenticated": true` und spiegelt deinen Token.

### Schritt 2: `Bruno Desktop` mit Secret-Variablen (`public`-Environment ohne Docker)

1. Öffne [collections/bruno/auth-hygiene-lab/](https://github.com/chatelao/api-schulung/blob/main/collections/bruno/auth-hygiene-lab/opencollection.yml) in Bruno Desktop und wähle das Environment **`public`** (Adresse: `https://httpbin.org`; oder **`local`** mit eigenem Container aus [Advanced A00](../advanced/A00.md)).
2. Öffne die Environment-Einstellungen (*Configure*):
   - Die Felder `basicPass`, `apiKey` und `bearerToken` tragen das Schloss-/Secret-Symbol (**`secret: true`**).
   - Im Git-Repository ist deren `value` leer (`""`). Wenn du eigene Laborwerte in Bruno Desktop eintippst, speichert Bruno sie **lokal verschlüsselt auf deinem Rechner** — die YAML-Datei im Repository bleibt frei von Geheimnissen!
3. Führe im Ordner **`Classic Auth`** die Requests (`01-basic-auth`, `03-api-key`, `04-bearer-token`; sowie `02-digest-auth` mit eigenem Container aus `A00`) aus.

> **Für Fortgeschrittene (Shell & `curl`):** Wie man Geheimnisse im Terminal mit `curl -K -` und `--netrc-file` vor der Shell-Historie schützt, erklärt [Advanced A03: Secret-Hygiene in der Shell](../advanced/A03.md).

## 4. Typische Fallstricke und Troubleshooting

| Fehlerbild | Ursache | Lösung |
| :--- | :--- | :--- |
| Request meldet `401 Unauthorized` nach dem Öffnen der Collection | Die Secret-Variablen (`secret: true`) wurden nach dem Klonen lokal noch nicht befüllt | Werte (z. B. `CHANGE_ME_LAB_HTTPBIN` für `local` oder eigene Testwerte für `public`) in Bruno unter *Environments* eintragen |
| Eine `.env`-Datei taucht in Git als neue Datei auf | `.env` liegt nicht im `.gitignore`-Filter | Prüfen, dass die Datei exakt `.env` heisst (nicht `.env.txt`) und in `.gitignore` steht |
| API-Key funktioniert nicht | Im Dropdown *Add to* wurde *Query Params* statt *Header* gewählt | Auf **Header** (`X-Api-Key`) umstellen |

## 5. Spickzettel (Cheat Sheet)

| Konzept | Merksatz |
| :--- | :--- |
| `secret: true` (Bruno) | Speichert Geheimnisse nur lokal, niemals in Git |
| **Base64** | Kodierung, **keine** Verschlüsselung |
| **Header vs. Query** | Credentials immer im Header (`Authorization` / `X-Api-Key`), nie in der URL |
| `.gitignore` | Schützt `.env` und Zertifikatsschlüssel vor versehentlichem Commit |
