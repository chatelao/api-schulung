# Modul 11: OpenID Connect (OIDC) — Discovery, JWKS, ID Token & `/userinfo`

## 1. Lernziele

Nach Abschluss dieses Moduls kannst du:
1. Die Aufgaben von **OAuth 2.0 (Autorisierung)** und **OpenID Connect (Authentifizierung)** anhand von **Access Token** vs. **ID Token** strikt **trennen**.
2. Identity Provider dynamisch über **OIDC Discovery** (`/.well-known/openid-configuration`) im Browser oder in Bruno anbinden, statt URLs fest einzutragen.
3. JWT-Header und -Claims visuell inspizieren und verstehen, weshalb **Lesen/Dekodieren ≠ Verifizieren** ist (Signaturprüfung gegen `jwks_uri` mittels `kid`).
4. Den OIDC-`/userinfo`-Endpunkt korrekt mit dem **Access Token** (niemals dem ID Token!) abrufen und `type: openIdConnect` in OpenAPI 3.1 modellieren.

## 2. Architektur und Kernkonzepte (anschaulich erklärt)

- **OAuth 2.0 (Access Token):** *«Was darf diese App tun?»* — Der Zugangsschlüssel für Fach-APIs (wie eine Hotel-Zimmerkarte).
- **OIDC (ID Token):** *«Wer bist du?»* — Der unterschriebene Ausweis des angemeldeten Benutzers für die App selbst.

**Kritische Sicherheitsregel:**
- Sende **niemals** ein OIDC-ID-Token als `Authorization: Bearer` an eine Backend-API!
- Umgekehrt beweist ein Access Token gegenüber dem Client allein noch keinen gültigen Benutzer-Login (seine Zielgruppe `aud` ist eine API, nicht deine App).

### Vergleichstabelle: ID Token vs. Access Token

| Merkmal | OIDC ID Token | OAuth 2.0/2.1 Access Token |
| :--- | :--- | :--- |
| **Zweck** | Identitätsnachweis für den Client | Berechtigung für APIs (Resource Server) |
| **Format** | Immer signiertes JWT (`Header.Payload.Signatur`) | JWT oder opaker Referenz-Text |
| **Zielgruppe (`aud`)** | **`client_id`** deiner App | Ziel-API (z. B. `api-lab-orders`) |
| **Darf an `/userinfo` oder APIs gesendet werden?** | **NEIN!** (Bleibt im Client) | **JA** (`Authorization: Bearer <access_token>`) |

## 3. Geführter Walkthrough (`Browser`, `Bruno Desktop` & `Lernstudio`)

### Schritt 1: OIDC Discovery & JWKS im Browser ansehen (sofort ohne Docker!)

1. Öffne **`https://demo.duendesoftware.com/.well-known/openid-configuration`** direkt im Webbrowser (oder lokal mit dem Container-Labor aus [Advanced A00](../advanced/A00.md) unter `http://localhost:8081/realms/api-lab/.well-known/openid-configuration`).
2. Du siehst die zentrale Visitenkarte des Identity Providers mit `issuer`, `authorization_endpoint`, `token_endpoint`, `userinfo_endpoint` und **`jwks_uri`**.
3. Öffne die dort verlinkte `jwks_uri` (`https://demo.duendesoftware.com/.well-known/openid-configuration/jwks` bzw. lokal `.../protocol/openid-connect/certs`): Dort stehen die **öffentlichen Schlüssel** (`kid`, `kty: RSA`), mit denen jeder Dienst prüfen kann, ob ein Token wirklich vom IdP unterschrieben wurde.

### Schritt 2: ID Token vs. Access Token inspizieren (Dekodieren ≠ Verifizieren)

1. Öffne im **Interaktiven Lernstudio** das Tab [3. OAuth 2.1 PKCE & JWT Inspektor](https://chatelao.github.io/api-schulung/#labs:oauth) und lade die Beispiel-Tokens (oder hole mit laufendem Container-Labor in Bruno `collections/bruno/oauth-pkce-lab/` ein echtes Token mit Scope `openid profile email`).
2. Vergleiche Header (`alg`, `kid`) und Payload (`iss`, `sub`, `aud`, `exp`, `scope`, `nonce`).
3. **Wichtig:** Ein JWT besteht aus drei Teilen mit Punkten (`Header.Payload.Signatur`). Die ersten beiden Teile sind lediglich Base64URL-Text — jeder kann sie lesen! Erst die kryptografische Prüfung des dritten Teils (Signatur) gegen den passenden `kid`-Schlüssel aus `jwks_uri` beweist Echtheit.
4. *(Mit Container-Labor `A00`):* Führe `01-user_info_coll-auth` in Bruno Desktop aus → Bruno sendet automatisch das **Access Token** an `/userinfo` und erhält deine Benutzerdaten (`200 OK`).

> **Für Fortgeschrittene (Shell & `curl`):** Discovery, Base64URL-Dekodierung mit `jq` und JWKS-`kid`-Matching im Terminal zeigt [Advanced A05](../advanced/A05.md).

## 4. Typische Fallstricke und Troubleshooting

| Fehlerbild | Ursache | Diagnose & Lösung |
| :--- | :--- | :--- |
| API / `/userinfo` lehnt Token mit `401` ab | ID Token statt Access Token als `Bearer` gesendet | Token-Claims prüfen (`aud`, `typ`); strikt das Access Token an APIs senden |
| Signaturprüfung scheitert nach Key-Rotation | Öffentlicher Schlüssel wurde statisch kopiert statt über `jwks_uri` geladen | Immer dynamisch über `/.well-known/openid-configuration` → `jwks_uri` auflösen |
| OIDC Discovery klappt in Bruno/Backend, aber im Browser nicht | CORS-Freigabe fehlt am IdP | `webOrigins` im Client prüfen |

## 5. Spickzettel (Cheat Sheet)

| Endpunkt / Claim | Bedeutung |
| :--- | :--- |
| `/.well-known/openid-configuration` | Automatische Konfigurationsadresse (OIDC Discovery) |
| `jwks_uri` | Öffentliche Signatur-Schlüssel des IdP (`kid`) |
| `iss` / `sub` / `aud` | Aussteller / eindeutige Benutzer-ID / vorgesehene Zielgruppe |
| **Dekodieren ≠ Verifizieren** | Sichtbarmachen der Claims ersetzt niemals die Signaturprüfung! |
